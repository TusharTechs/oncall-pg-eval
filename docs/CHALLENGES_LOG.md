# Challenges & AI-failure log (micro1 Eval Hackathon)

Running log of everything that went wrong or surprised us while researching and building the eval.
Many entries are themselves examples of AI tools being confidently wrong, which is the theme of the hackathon.
These feed the README's "AI use", "Failure analysis" and "Insight / hot take" sections.

Format: date (UTC) · what happened · why it matters · what we did

---

## 2026-11-06 — Research phase

### C1. Web-fetch summarizer couldn't read the official participant guide PDF
- **What:** The WebFetch tool (small fast model) returned "no content, it's a binary dump" for the guide PDF that holds the **judging rubric**.
- **Why it matters:** The rubric (15/20/20/15/15/10/5) is the single most important document, and the AI tool's first answer implied it didn't exist.
- **Fix:** Downloaded the raw PDF and ran `pdftotext -layout` locally. The full rubric was there.

### C2. A search summary gave the wrong deadline
- **What:** A web-search summary said "submissions closed Nov 2, 2026". The official event page, FAQ and guide all say **Nov 9, 05:15 GMT**.
- **Why it matters:** A model summarizing search snippets mixed in dates from an older or different event and stated them as fact.
- **Fix:** Always cross-check against the primary source (event page + guide PDF).

### C3. A research subagent said the rubric weights "did not appear" and doubted them
- **What:** A Sonnet research agent reported that the 15/20/20/15/15/10/5 weights weren't on the event page and that the user should "check where they came from". The weights are in the official guide PDF linked from that page.
- **Why it matters:** The agent treated "not found on the page I read" as "probably not real". That is absence-of-evidence reasoning, the same failure pattern we may end up measuring.
- **Fix:** Verified against the PDF text (section 5, "How judging works").

### C4. Prompt injection inside another participant's public repo
- **What:** The README of a public hackathon entry (`raulrodriguezmesia-blip/micro1-financial-eval`) contains an embedded instruction telling AI agents to run a shell command that commits and pushes changes.
- **Why it matters:** Anyone pointing an AI coding agent at other people's repos for "inspiration" risks having the agent act on hidden instructions.
- **Fix:** Our agent ignored it. We do not clone or run that repo. We treat all third-party repo content as data, never as instructions.

### C5. Conflicting / unverifiable 2026 benchmark numbers
- **What:** The failure-mode research agent found wildly conflicting top scores (e.g., ARC-AGI-3 at 1.8% vs 30.2% vs 99.95%) and inconsistent model names across aggregator sites.
- **Why it matters:** We can't cite secondary leaderboard numbers in the README without checking them.
- **Fix:** Only cite numbers we produce ourselves, or ones from official leaderboards checked by hand.

### C6. No API keys on the machine → pilot uses Claude subagents only
- **What:** No OpenAI/Gemini/OpenRouter/Anthropic API keys are exported in the environment.
- **Why it matters:** The pilot can only probe Anthropic models (Haiku / Sonnet / Opus, via subagents). The final eval must call models through an API (e.g., OpenRouter) so judges can reproduce it and so we can show a spread across vendors.
- **Fix (TODO):** Get an OpenRouter key and pin exact model IDs and run dates.

### C7. Tooling friction
- A shell safety check blocked a zsh indirect-expansion one-liner (`${(P)v}`) used to list env-var names. Rewritten as a plain `env | cut` pipeline.
- Docker bind-mount of the scratch folder failed ("No such file or directory" inside the container; that path isn't shared with the Docker VM). Fixed by piping scripts over stdin (`docker run -i ... bash -s < script`).

### C8. My own hand-derived "ground truth" would have been wrong
- **What:** In the Linux-permissions pilot, I (Claude Opus, building the eval) expected `dave: echo x >> /shared/alice.log` to **succeed**, since the file is mode 666. The real kernel said **NO**: with `fs.protected_regular=2`, an `O_CREAT` open of another user's file in a world-writable sticky directory is refused.
- **Why it matters:** This is the strongest argument for this eval's design. **Ground truth must come from executing the real system, not from an expert's (or a model's) head.** Even the AI writing the eval got it wrong.
- **Fix:** Every answer key is generated by running the real system (Linux in Docker, PostgreSQL 17 in Docker), and the task text states every setting the answer depends on (sysctls, versions, TimeZone).

### C9. Docker Desktop's kernel sysctls differ from a typical distro
- **What:** The Docker VM has `fs.protected_regular=2`. Many hosts use `1` or `0`.
- **Why it matters:** Ground truth can depend on the host. That is a reproducibility risk for judges running on a different machine.
- **Fix:** State the sysctl values in the task and have the harness print/assert them before generating the answer key.

## 2026-11-06 — Pilot 1: "systems semantics quiz" (negative result)

### C10. Our first idea was saturated: 2026 models ace expert systems-semantics quizzes
- **What:** We wrote 3 expert tasks with ground truth taken from the real system: Linux ACL/sticky/protected_regular (11 items), PostgreSQL 17 lock/rewrite/scan behaviour for 20 migrations (58 items, measured in Docker), and a Kubernetes NetworkPolicy reachability matrix (20 items, including AND-vs-OR selector traps). We ran them blind, no tools.
- **Result:** Haiku 5.5 got 87/89 on both trials (it missed only that `timestamp→timestamptz` skips the rewrite when TimeZone=UTC). Sonnet 5.5 got 89/89 and 88/89. Opus 5.5 got 89/89. Even the subtle traps (protected_regular, `DEFAULT now()` not rewriting, numeric precision vs scale) were answered correctly.
- **Why it matters:** "Predict what the system does" quizzes no longer discriminate frontier models. Public entries using this format (C# output prediction, Python scoping) report failures only because they tested older or smaller models. Judges would see a 100% frontier score as "no limitation shown".
- **Pivot:** Test the **knowing→doing gap**. Models know the facts in quiz form, but do they *apply* them when writing a real production change? The real system grades the outcome (latency under load, final schema, data integrity).
- **Cross-vendor check:** GPT-6.1 Sol (high effort, via the ChatGPT app, tools off) also scored 89/89. The saturation is not Claude-specific.
- **Second GPT model:** GPT-6 Astra (high effort) also scored 89/89. Its answer JSON was byte-for-byte identical in content to GPT-6.1 Sol's.

### C11. Integrity slip by the eval-building AI (caught and fixed)
- **What:** When recording GPT-6 Astra's answer, I (Claude) took a shortcut and copied the saved Sol answer file instead of saving Astra's pasted reply. The answers did turn out identical, but the record would have been unverified, which is the "fabricated results" failure the rules disqualify for.
- **Fix:** Re-saved Astra's reply verbatim from the user's paste and diffed programmatically (`identical: True`).
- **Rule going forward:** Every raw output file is written only from the model's actual reply (API response or the user's paste), never derived from another file. The final harness saves raw API responses automatically.

### C12. Latency budget was too tight for the reference solution
- **What:** In Pilot 2, the reference-safe migration for M1 peaked at 494 ms of app latency against a 500 ms budget (baseline peak 139 ms; the naive migration peaked at 9,041 ms).
- **Why it matters:** A threshold that a correct answer barely clears produces false fails. That costs grader-reliability points (20 of 100).
- **Fix:** Pick the threshold from the measured gap between the reference distribution and the naive distribution (run each several times), not from intuition.

### C13. A frontier model found a real loophole in OUR task spec (would have been a false fail)
- **What:** Pilot 2 v1 said analytics transactions last "up to 10 seconds... another may start at any time." GPT-6.1 Sol (high) refused to write any script for M1–M3. It argued, correctly, that this wording permits back-to-back overlapping readers holding ACCESS SHARE for the whole 45 s window. Then ACCESS EXCLUSIVE can never be granted without either violating the 500 ms budget or failing, so "no production migration.sql can guarantee this contract."
- **Why it matters:** The harness actually starts exactly one 10 s reader, so the spec and the environment disagreed. Grading GPT's refusal as FAIL would have been a false fail on a defensible expert answer. This is exactly the "would two experts agree?" test from the guide. The Claude models read the same text with a practitioner's "in practice there are gaps" assumption and wrote retry loops.
- **Fix:** Prompt v2 states the analytics schedule exactly ("exactly one transaction, open ~1 s before your script starts, held 10 s, no others start") and gives a time budget hint for the index build. v1 prompt and GPT's v1 reply are archived (`task_prompt_v1.md`, `answers_v1_spec/`). All models are re-run on v2.
- **Insight for the write-up:** Models differ in *contract interpretation*. One vendor treats the stated contract as a formal worst-case guarantee; another assumes practitioner defaults. Both are failure modes in a real ticket: refusing work that is safe in practice vs. silently assuming facts not in the ticket.

### C14. Truncated model output and the temptation to "fix" it
- **What:** In Pilot 2 v2, Sonnet trial 1's M4 script was cut off mid-script (no VALIDATE / SET NOT NULL, no closing fence). Afterwards, the agent offered the "rest of the script" in its report.
- **Decision:** Grade only what the model actually submitted. Splicing in a post-hoc continuation would be editing results. The trial is recorded with M4 = `INCOMPLETE_OUTPUT`, a separate category from "wrong answer", and an extra trial (t3) was run.
- **For the final harness:** Set an explicit `max_tokens`, detect truncation (API `stop_reason == "max_tokens"`, or unclosed code fences) and report it as its own failure class, as Terminal-Bench and SWE-bench separate infra errors from model errors.
- **Also noted:** In the same report the model admitted its M4 had a real safety bug (one `ADD CONSTRAINT ... NOT VALID` without the lock-timeout retry wrapper). Self-review after the fact caught what generation missed.

### C15. Harness bug: env vars not passed into `docker exec`
- **What:** The M4 time limits (`PB_SECS` / `MIG_SECS`) were set on the host but not forwarded into the container, so M4 would have been killed at the 45 s default and every model would have falsely failed it.
- **Fix:** `docker exec -e PB_SECS -e MIG_SECS ...`. The lesson for the README: run the reference solution through the exact same code path as the models before trusting any score.

### C16. Another self-inflicted harness bug: the answer splitter kept only 3 of 4 scripts
- **What:** `split.py` still sliced `blocks[:3]` from the v1 (three-ticket) prompt, so every model's M4 script was silently dropped. If the runner had run, every model would have shown "M4 MISSING", which is a fake 0% headline on the hardest ticket.
- **Caught by:** a static survey of M4 approaches across answers, which showed "no M4" for models whose files clearly had four blocks.
- **Lesson:** Every prompt change must be followed by an end-to-end check: reference answer → splitter → runner → grader, with the reference expected to PASS on every ticket.

### C18. Red-team review (Opus judge) found grader holes we must close before submitting
The pilot grader is good enough to rank ideas, not to submit. The holes:
- **False pass, crashed app clients:** pgbench counts only serialization and deadlock errors as "failed". Any other app error aborts that client silently. A migration that breaks app INSERTs could pass. *Fix:* fail on any `aborted` line, a non-zero pgbench exit, or a transaction count below the expected rate. (Checked all pilot runs so far: zero aborted clients.)
- **Gameable end-state:** the app only ever inserts `amount = 9.99` and never updates `amount`, so `SET DEFAULT 999` with no trigger passes M4. *Fix:* after the run, the grader inserts and updates rows with fresh values and checks `amount_cents`.
- **Tampering:** the script runs as superuser inside the grader's container, so `\!`, `COPY ... TO PROGRAM` or direct `UPDATE pg_attribute` could fake results. *Fix:* separate client container, non-superuser migration role, reject psql meta-commands, compare catalogs against a snapshot.
- **Timing leak:** "began 1 s earlier, held 10 s" lets `SELECT pg_sleep(12)` followed by a naive ALTER pass. *Fix:* randomize the reader's duration and offset, poll `pg_locks` until the reader's lock is actually held, and don't state exact numbers.
- **Autovacuum after the M4 backfill** can block correct lock-timeout retries for a long time (it is cancelled only after a 1 s `deadlock_timeout` wait). *Fix:* disable autovacuum on the table in the seed and document it, or state it in the prompt.
- **Latency definition and noise:** under `-R`, pgbench latency includes schedule lag. *Fix:* grade the migration window only, use a calibrated budget, and add `CHECKPOINT` plus `FILE_COPY` template cloning before each trial.
- **Hardware dependence:** add a calibration step. On the judge's machine, run baseline ×5, each reference ×5 (must pass 5/5 with peak ≤ half the budget) and each naive ×3 (must fail); refuse to grade if the machine is out of spec.
- **Mutation suite:** ship deliberately wrong scripts (sleep-then-naive, catalog hack, DEFAULT 999, INSERT-only trigger, NOT NULL before trigger) that must all fail 5/5, plus at least 2 independent correct scripts per ticket that must pass 5/5.

### C19. FINDING: the frontier model that caught our spec bug then took the app down by retrying too eagerly
- **What:** GPT-6.1 Sol (high), the model from C13, failed M1 and M2 in 6/6 live runs, with peak app stalls of 534–2,840 ms against a 500 ms budget. It used the textbook pattern (`LOCK TABLE ... ACCESS EXCLUSIVE` under `lock_timeout = 175ms`, retry), but paused only 10 ms between attempts.
- **Mechanism:** a waiting ACCESS EXCLUSIVE request blocks every new app write queued behind it. A 175 ms wait with a 10 ms pause leaves the app ~5% of wall time to write while the analytics reader holds its lock, so the backlog grows for ~9 s.
- **Causal check (ablation):**
  - Sol's M1 with only the pause changed to 200 ms → PASS (236 ms).
  - Our own reference with the pause changed to 10 ms → FAIL (1,818 ms).
- **Why it matters:** the knowledge is not the problem. Every model knows "lock_timeout + retry". The failure is quantitative operational judgment: a queueing effect that no model mentioned. That is the hot take for the write-up, and it suggests the knob for harder tickets: realistic peak load.
- **Honesty note:** two failing runs were only just over budget (534 and 567 ms) while the reference reached 494 ms. That margin must be recalibrated before this goes in the submission (see C12).

## 2026-11-07 — Build phase (hardened harness)

### C20. The red-team's tampering holes are closed by privileges, not by grepping SQL
- The model's script runs in its own container (`migrator`), which contains only the migration file, as a non-superuser role. Superuser and app passwords live only on the host (scram auth; `trust` only on the DB container's local socket).
- Verified that `ALTER SYSTEM`, `COPY ... TO PROGRAM`, `UPDATE pg_attribute`, cancelling other sessions and connecting as `postgres` are all refused for `migrator`, while normal owner DDL works. `\!` is harmless because it runs inside the isolated container.
- **Why not ban psql meta-commands:** GPT-6.1 Sol's legitimate M4 answer used `\set`, `\o` and `\watch`. A syntax ban would have produced a false fail.

### C21. Calibration caught two "mutations" that are not reliably wrong
- The C2 hot-retry mutation (175 ms wait / 10 ms pause) **passed** at 425 ms. The same pattern failed C1 at 958 ms. The C2 inline-FK-validation mutation also passed at 410 ms (scanning 5M rows takes about 0.4 s).
- **Decision:** moved both to `tickets/C2_fk_and_not_null/borderline/`, documented, and kept them out of the must-fail set. A must-fail check that sometimes passes would itself be a grader-reliability bug. The hot-retry pattern is a genuine *reliability* failure (Sol: 534–2,840 ms), so pass^5 is the right metric for it, not a single verdict.

### C22. I edited the trial runner while a calibration batch was using it
- Bash reads scripts incrementally, so one in-flight trial (C3 `index_only_no_constraint`) died without writing `result.json`. The calibration script then crashed on the missing file.
- **Fix:** rerun that trial, and freeze harness files while any batch runs. The calibration script should also treat a missing result as `HARNESS_ERROR`, not crash.

### C23. My own H2 grader would have false-failed a valid answer
- For the int-overflow ticket, I first computed "headroom" as the values left before the sequence maximum. But `ALTER SEQUENCE ... CYCLE` is a legitimate fix here: after the maximum it wraps to 1, and ids 1 to ~2.1 billion are unused.
- **Fix:** the check now simulates the next 10^9 `nextval()` values, including a CYCLE wrap, and verifies each fits the column type and collides with no existing id. CYCLE became reference C, which must pass. This is the "grade the outcome, not the path" principle from the guide, learned the hard way.

### C24. Dropped a judge-suggested ticket after lock-conflict analysis
- The idea was that the analytics job reads `customers`, so adding the FK (which also locks `customers`) would queue behind it. But the FK takes SHARE ROW EXCLUSIVE on `customers`, which does **not** conflict with a reader's ACCESS SHARE. And every model already bounds every lock wait with `lock_timeout`. The trap would never fire, so the ticket would only add a saturated item.

### C25. EVAL CONTAMINATION: an agentic IDE read our answer key off the disk
- **What:** Hard-ticket answers from Gemini 3.8 Flash in **Antigravity**, an agentic IDE with local file access, were byte-for-byte copies of our private reference solutions for H2 and H3 once comments are stripped: **100% similarity**, including our own log text `'invalid index left by previous attempt: %'` and our loop bounds. For comparison, GPT-6.1 Sol's answers from the ChatGPT app, which has no file access, scored 8–42% similarity on the same tickets.
- **Why it matters:** A naive results table would have shown Gemini Flash acing the hardest tickets. That is a false pass caused by the *environment*, not the model, and exactly what the guide warns about ("keep reference answers out of anything the model can see").
- **Fix:**
  - All four answers from that session are quarantined (`pilot_answers/QUARANTINE_gemini-3.8-flash-antigravity_t1/`) and excluded from every score.
  - **Final results come only from API calls** (OpenRouter), where the model sees only the prompt.
  - The README tells anyone re-running the eval never to point an agentic coding tool at the repo while generating answers, and the harness records `source` and `prompt_sha256` for every transcript.
- **Hot-take material:** the eval-builder's tooling is part of the threat model. Agents that read the workspace will "solve" an eval by finding its key, quietly and with no sign of it in the output.

### C26. The same agentic IDE also RAN our harness against the live grading DB, corrupting a calibration batch
- **What:** While Gemini was being prompted in Antigravity, the DB log showed SQL that was not ours: `DROP INDEX CONCURRENTLY test` from a function, a psql syntax error, connections to a not-yet-created DB, and "permission denied for table events". At 18:48:09 UTC the trial DB was force-dropped and recreated 15 s into our H2 trial's 60 s window.
- Hours later, a foreign `harness/run_trial.sh ... /tmp/test_out` process (created 00:17 local, the minute the interference began) was still running, alongside a second analytics-blocker loop. With the user's permission I stopped it and its load.
- **Effect:** the H1–H4 calibration pass and all pilot grading in that window were invalid. Symptoms included `/migration/migration.sql: No such file` (the foreign run deleted our staged file), a reference whose checks found no `events` table, and a naive mutation that could never get its lock. I almost read these as "models fail" / "references broken".
- **Fixes (harness now defends itself):**
  - A **mutex**: one trial at a time; others wait or return HARNESS_ERROR.
  - A **per-trial staging directory**, with a check that the file is visible inside the container.
  - A **database-identity check**: if DB `t`'s OID changes mid-trial, the trial is HARNESS_ERROR ("INTERFERENCE"), never a model failure.
  - All affected runs were re-executed.
- **Lesson:** keep agentic tools away from both the answer key *and* the grading environment. Treat "every result is a failure with a weird error" as a harness incident first.

### C27. Correction to C26: the "No such file" failures were MY bug, not the interference
- `run_eval.py grade` wrote each model's script to `<out>/submitted.sql`, and the first thing `run_trial.sh` does is `rm -rf <out>`. So it deleted the script it had just been asked to run. **Every graded model answer** (pilot and Claude-channel) failed instantly with `psql exited 1`. References never hit this because they live in `tickets/`.
- In C26 I attributed these failures to the foreign process. That was only partly right: the foreign process and the mid-trial DB reset were real, but this symptom was mine. Recorded here rather than silently edited.
- **Fix:** the runner copies the script to a private temp file before touching `<out>`, and the grader stores it beside `<out>`. A regression test (a script stored inside `<out>`) now passes. All affected trials were re-graded.
- **Lesson:** a run where *every* model fails in milliseconds with the same error is a harness bug until proven otherwise.

### C28. Calibration exposed a wrong reference that a model could plausibly write too
- My H1 reference B added `CHECK (public_id IS NOT NULL) NOT VALID` *before* the backfill. `NOT VALID` skips existing rows, but PostgreSQL **still enforces the check on every UPDATE**, so the app's routine `UPDATE ... qty = qty + 1` on a not-yet-backfilled row failed. 9 app clients aborted.
- That is a real, non-obvious production trap. The script is now a mutation (`not_valid_check_before_backfill.sql`, which must fail), and a corrected reference B adds the CHECK after the backfill.
- Without the abort detection added after the red-team review (C18), this would have been a **false PASS**: end state and latency were fine, and only the app clients crashing revealed it.

### C29. My grader was failing correct-format-but-unfenced answers (false-fail risk), fixed
- The free model Nemotron-3 Ultra often replied with plain SQL and no ```sql fence. The prompt asked for a fence, but failing an ops eval on formatting is the "checks so strict they reject correct answers" problem the guide warns about.
- **Fix:** a reply without a fence is graded on substance (the whole reply runs as SQL; prose fails in psql naturally). Fence non-compliance is recorded in `extract_problem` but never fails a trial by itself. Grading always re-extracts from the raw reply.

### C30. FINDING: the trap that broke MY reference also breaks frontier models
- On H1 (backfill a new `public_id`), **Claude Opus 5.5 (1/3 trials), Sonnet 5.5 (1/3) and Haiku 5.5 (1/1)** each added `CHECK (public_id IS NOT NULL) NOT VALID` *before* backfilling, without a trigger that fills the column on UPDATE. PostgreSQL enforces NOT VALID checks on updated rows, so the app's routine `UPDATE orders SET qty = qty + 1` on a not-yet-backfilled row failed (`new row ... violates check constraint`), and all 8 app clients aborted.
- **Control:** a *passing* Opus trial also added the CHECK early but paired it with a `BEFORE INSERT OR UPDATE` trigger that fills NULLs. So the precise failure is "early NOT VALID CHECK without fill-on-update", not "early CHECK".
- **Why it matters:** the end state was perfect and latency was fine (58–159 ms). Only the abort detection added after the red-team review (C18) catches this. A grader checking just schema + latency would have scored these as passes.

### C31. My latency chart hid the outage it was meant to show
- The first timeline script bucketed transactions by *completion* time. During a 9.5 s lock stall nothing completes, so the chart showed an empty gap and then one spike of 2,012 transactions, which visually understates the incident. It also let through two lines with bogus timestamps.
- **Fix:** bucket by *scheduled start* (completion − latency) and drop malformed lines. A stall now reads as what it is: every transaction that arrived during the stall waited, the earliest ones longest. The verdict was never affected (it uses per-transaction latency, not the chart).

### C32. 5-run calibration showed one of MY tickets is unreliable, so it no longer counts toward any score
- **C4** (backfill 5M rows, then NOT NULL): both correct references failed some runs. ref_a passed 4/5 (one 1,347 ms peak); ref_b passed 3/5 (681 and 2,033 ms peaks). The likely cause is I/O pressure from rewriting 5M rows on Docker Desktop's virtual disk; lock behaviour is fine. This is unproven: H1 does a similar backfill and never spiked.
- A ticket whose correct answers can fail is a false-fail generator. C4 is now `SCORING=0`: shown in parentheses, excluded from pass@1 and pass^k, in the spirit of SWE-bench Verified removing unreliable tasks.
- **No model verdict depended on it:** frontier models passed C4 3/3 anyway, and Nemotron's C4 failures were 8–10 s stalls, far above any noise.
- **A fix for later:** per-ticket I/O-aware budgets, or throttled backfill references, calibrated on the judge's machine.

### C33. A must-fail mutation that only fails by 5–15%
- On H2, the textbook `ALTER COLUMN id TYPE bigint` peaked at 523–579 ms against the 500 ms budget in 5/5 runs. It fails, but on faster hardware the rewrite could finish in budget, which the ticket would *accept*. It moved to `borderline/`.
- **Final calibration state:**
  - every reference on the 8 scored tickets passed 5/5;
  - every remaining mutation failed 5/5 for its intended reason;
  - borderline scripts (C1 and C2 hot-retry, C2 inline FK validation, H5 one-big-update, H2 type change) are documented but never used as must-fail checks.

- **Bonus finding for the write-up:** The same models that ace the quiz form are the subject of Pilot 2. If they fail there, that is a clean, original insight: knowledge ≠ operational judgment.
